## 3) الجواب: هل يتغير pollfd بين PEEKDATA وأثر القرار؟

- **هيكليًا [MEASURED]: نعم، النافذة موجودة.** بعد آخر PEEKDATA (channel_hooks.rs:22–30) و`return true` (:36)، يستأنف المشرف الـtracee (SYSEMU) فيدخل `poll()` الحقيقي **الذي ينسخ النواة مصفوفة pollfd من ذاكرة الـtracee الحية لحظة الدخول** (copy_from_user النووي) — اللقطة المتحقق منها لا تُقارن بلا ما نُفِّذ عليه. مدخل `count` سجلي ثابت؛ **المحتوى الذاكري هو الوحيد الراكض.**
- **قراءة 32-بت الدنيا (`entry as u32 as i32`, :31) متسقة مع النواة** (أول حقل `int fd` في struct pollfd) — كتابة 64-بت خبيثة تُحكم على الكلمة الدنيا نفسها التي تقرأها النواة؛ لا التفاف هناك.
- **قابلية الاستغلال [INFERRED — غير مثبتة ديناميكيًا هنا، ولا بد من قول ذلك]:** شرط الضرر أن يحمل الـtracee وصفًا `>2` قابلًا للمراقبة (جاهزية = قناة معلومات جانبية زمنية). إن كان ثابت ginux «لا وصف >2 للـtracee أبدًا» قائمًا، فإن أسوأ سباق = POLLNVAL (غير ضار) والبوابة عمق دفاعي. أي العالمين صحيح لم يُقضَ فيه هنا — يحتاج تدقيق ثابت جدول الواصفات (T3 أدناه). **لا إعادة قراءة بعد الاستئناف ولا تثبيت للقيم في الكود الحالي — الفجوة هيكلية وإن كان الوصول إليها مشروطًا.**

## 4) تصميم PoC متعدد الخيوط (نص فقط — بلا كود مكتوب)

**T1 — كاشف التباعد (الجوِهر):** tracee بخيطين: `main` يلف `poll(fds, 2, 0)` حيث `fds[1].fd` يُبدّله الخيط الشقيق بين 0 ورمز X بلا توقف. المشرف (harness اختبار، ليس كودًا يُشحن): يلتقط لقطة PEEKDATA أثناء التحقق، وبعده — عند توقف خروج الـsyscall — يعيد PEEKDATA للفُتح نفسها. **معيار الإثبات:** ≥1 تكرار (من 10^6) تظهر فيه revents≠0 للرمز X مع لقطة تحقق تظهر 0 ⇒ السباق اكتُسب فعلًا. **معيار النفي:** صفر تباعد عبر كل التكرارات + قياس عرض النافذة (T2) ⇒ خطر محدود الحد الأعلى.
**T2 — قياس النافذة:** timestamps حول حلقة PEEKDATA وحول الاستئناف في المشرف ⇒ توزيع زمن «تحقق→أثر»؛ احتمال الربح ≈ معدل التبديل × النافذة؛ يحدد N المطلوب لـT1.
**T3 — مسبار ثابت الواصفات:** محاولة منح الـtracee وصفًا >2 عبر المسارات المسموحة/المحاكاة فقط (بلا اختراق) ⇒ يحدد إن كان متغيّر الهجوم (X حقيقي) قابلًا للبناء أصلًا في نموذج ginux. نتيجته تحسم الخطورة: «قناة جانبية ممكنة» مقابل «عمق دفاعي فقط».

## 5) مسودة تعليق مراجعة (إنجليزية — **غير منشورة**، قرار النشر لAbdelhafid)

> **Question on `bootstrap_poll_allowed` (PR #207): is the validated pollfd snapshot re-checked after resume?**
>
> In `channel_hooks.rs:13–37`, `bootstrap_poll_allowed` reads each pollfd slot from tracee memory via `PTRACE_PEEKDATA` and rejects any descriptor `> 2`; `dispatch.rs:90–92` gates `SYS_POLL` on it. My reading is that the allow/passthrough decision is taken from this PEEKDATA snapshot, while the kernel copies the pollfd array from live tracee memory at `poll()` entry after the supervisor resumes the tracee — so a sibling tracee thread that rewrites a slot between the last PEEKDATA and the kernel copy would be validated as one set and executed as another. With the low-32-bit read (`entry as u32 as i32`) matching what the kernel sees, the residual question is whether the tracee can ever hold a descriptor `> 2`: if the fd-table invariant holds, the worst case is a harmless POLLNVAL; if any path grants one, this looks like a readiness side channel on a sensitive descriptor.
>
> Is the intended mitigation that the tracee cannot hold descriptors > 2 (in which case a note in the doc-comment would help), or is re-validation after resume planned? A two-thread toggle PoC (sibling flips `pollfd[1].fd` between 0 and a sentinel while `main` loops `poll`) with a post-exit PEEKDATA divergence check would settle it dynamically.

> **Title:** PR #207 (`bootstrap_poll_allowed`): is the PEEKDATA snapshot decision intended to be final?
>
> Live state (checked 2026-11-06): #207 Open, head `e7f5f552`.
>
> The gate: `bootstrap_poll_allowed` (channel_hooks.rs:13–37, via dispatch.rs:89–96) decides SYS_POLL from a PEEKDATA snapshot of the tracee's pollfd array: more than 16 fds ⇒ deny; any slot with fd > 2 ⇒ deny; PEEKDATA failure ⇒ deny — fail-closed at snapshot time. The kernel, however, copies the pollfd array from live tracee memory when the syscall actually executes, after the supervisor resumes it; nothing re-reads or pins the validated values after the last PEEKDATA.
>
> So the decision that reaches the kernel is taken from one memory sample, and the syscall that runs may not be the one that was validated. Whether that gap can matter depends on an invariant we cannot settle from outside: if a ginux tracee can never hold fd > 2, the worst a stale-pass can do is poll an invalid descriptor — a harmless POLLNVAL — and the gate is defense-in-depth; if any path can grant one, the readiness report becomes a time channel the snapshot decision no longer covers.
>
> Question for the author/maintainer: is "a tracee never holds fd > 2" intended as the only guarantee here? If yes, would a one-line doc-comment on `bootstrap_poll_allowed` stating that the snapshot is not re-checked after resume be acceptable? If not, would a cheap re-validation of the slots after the last PEEKDATA be worth considering? No exploit is claimed or implied.
